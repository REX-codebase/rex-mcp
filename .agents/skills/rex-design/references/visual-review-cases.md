# Visual review cases

Read this reference only when a trigger fires: (1) the brief or implementation includes a visual claim that needs one of these checks - data relationships, physical or causal scenes, transformations, continuously changing controls, animation, or multi-state rendered evidence; or (2) the work touches one of the specialized interaction workflows under Interaction workflow cases below. Select the applicable cases; this is not a checklist for every design task, and pages without either trigger should not load it. The general review protocol - the frozen width range, host-framed captures, the first-time walk, and KEEP / CHANGE / CUT critique - lives in `../SKILL.md`; this reference adds only the specialized cases below.
## Failure classes to test before polishing

Treat each critique as a transferable failure class rather than adding a rule for one object or scene. Record the claim, evidence, counterexample and next test in a review ledger. These checks are not a pass certificate; select the ones relevant to the brief and test their actual rendered and interactive states.

- **Verdict strength and negative geometry:** match the final status wording to the strongest claim the source actually establishes: "no path" is different from "not verified," and an unknown status is different from a confirmed absence. In a route, dependency or connectivity diagram, do not draw a dashed or red connector through a segment that does not exist; color and dash alone still read as a connection. End the known path at the last reached node, isolate the unreachable target with space, and put the source and freshness caveat beside that break. Test the drawing with its labels hidden, then restore accessible text and check the source-specific wording at delivery size. A correct data label does not rescue a visually false relationship.
- **Evidence drift:** a source assertion, control label, accessibility text, receipt or animation frame cannot prove a settled visual or service state. Compare the exact claim to the same-crop pixels or service receipt at the claimed time, size and delivery frame. Mark untested claims unknown.
- **Coordinate and causal mismatch:** related marks, objects and effects need one declared coordinate system, transform, source and ordering rule. Derive dependent geometry from shared parameters; test boundaries and intermediate/reversed states. A mask or explanatory disclaimer cannot repair contradictory relationships. Use a defensible model if claiming physical behavior; otherwise describe the abstraction honestly.
- **Responsive geometry drift:** preserve intended shape proportions and relationships across aspect ratios and the host frame. Recompute dependent geometry together, not just the focal SVG or image. Check narrow and wide pixels for distortion, overlaps, clearance and recovery.
- **Control-semantic drift:** write the invariant, zero state and end state before styling. Exercise start, intermediates, end, reverse, keyboard and reduced motion. Verify the visible effect matches the value and label, not merely the event handler.
- **Scene identity under selection:** when a control claims to change one physical material or object, keep the surrounding scene stable: hands, tools, light and other materials must not change with it. A whole-frame color grade is a mood choice, not evidence of selecting cloth or another material. Compare identical crops at each state and name the effect truthfully if the scene cannot preserve that boundary.
- **Promised consequence:** a state change that only recolors or renames the same asset is not a new visible outcome. Hide the labels and compare settled frames to a plain baseline: what subject-specific consequence can the viewer see? The headline must also have an observable referent in the page; if the page promises a person-centered result but only shows a generic object, show the person-specific consequence or narrow the claim.
- **Idea substitution:** a decorative label, reveal, frame, generic layout or animation is not a second consequence. Ask what changes because of the central rule and whether a viewer could see that result without an explanation. Compare live references for mechanisms and fit, not their surface grammar.
- **Plausibility and state integrity:** inspect impossible intersections, detached shadows, occlusion, missing data, stale reviews and optimistic statuses according to the page's own premise. State which facts are modeled, simulated, observed or confirmed by a service.
- **Transformation custody:** if a before/after promises a new arrangement, conserve the original entities and any quantities the story depends on. Give them one coordinate system, consistent units, visible paths or reconstructible positions, and an honest account of what moved, remained fixed, became constrained, or could not move. A disappearance is not a mechanism. If the benefit is space or absence, show the opening and its boundaries rather than filling it with a new decorative object. Hide the headline and explanatory label while judging whether the visual still proves its central claim. A clean but idealized animation must not imply that every real constraint is movable.
- **Material-vocabulary break:** enumerate the visible primitives in the before and after states. If the result needs a solid stroke, silhouette, glyph, shadow or object not built from the conserved starting pieces, reject the claimed transformation or explicitly disclose the added element. Compare the rendered pixels, not only counts in code.
- **Stock-icon payoff:** hide the headline and labels, then ask whether the reveal is an expected symbol that could stand for any brand. A legible arrow or checkmark is not necessarily an original idea; seek a consequence specific to the subject and its rules.
- **House-style convergence:** compare recent outputs side by side. If unrelated briefs repeatedly become the same headline/caption/dark boxed stage/control, sketch a different page structure and narrative rhythm before revising the central graphic. Change layout, pacing and art direction for a reason tied to the brief, not random decoration.
- **Light/shadow source break:** a cast shadow must derive from the same object's geometry, receiver plane and light vector as the lit facets. Detached decorative dark shapes are not evidence of a consistent physical scene; remove them or derive and inspect their projection through the motion states.
- **Decorative/content collision:** evaluate guides, rules, overlays and framing as geometry, not neutral decoration. At each viewport and state, inspect whether they run through glyphs, controls or focal shapes; move or remove them rather than relying on their thinness or muted color. A rule may intentionally structure space, but should not accidentally slice the promised subject.
- **Weak resolved state:** compare the initial and resulting frames without labels at the same viewport. A technically legible result that loses scale, contrast, placement or visual energy has not earned its reveal. Redesign the destination and the path together, including how they use the first viewport, before polishing the transition.
- **Reveal spoilers:** inspect title, helper copy, button, footer and accessibility text together. Provide enough instruction to operate the page without printing the visual answer before a discovery; put the precise answer in the appropriate completed state and keep accessible instructions honest. Hiding necessary information from assistive technology is not a fix.
- **Interaction-form convergence:** changing a dark stage to a light stage does not break a formula when unrelated studies remain a two-state showpiece with the same title, caption and toggle. Sketch a different user action or narrative rhythm, such as choosing, arranging or exploring, only when it serves the subject. Verify real agency, keyboard access, feedback and recovery; do not add fake interactivity for novelty.
- **Agency without an outcome space:** count reachable outputs, not just interactive controls. When free choices yield mostly incoherent combinations or dead ends, constrain the language or data model so each permitted path has a meaningful consequence; show why a choice belongs to the subject. Test several ordinary paths, long combinations, removal and dead ends, not only one curated happy path. If a constraint changes the promised freedom, say so.
- **Feedback away from action:** on desktop and narrow viewports, inspect both the control and its result at the actual moment of use. If the result is offscreen or detached, give an immediate local response that names the change, and provide a clear route to the fuller result without forcing a hunt. Keep that response accessible and consistent with the distant state; verify on a short mobile viewport and with keyboard focus.
- **Evidence-set coherence:** compare every cited rendered frame to the exact source revision and capture context it represents. A task-bound PNG is not automatically current-source proof: edits between screenshots, even a small alignment correction, invalidate a mixed before/after set. Re-capture the affected states from one revision, then verify the settled pixels and any host frame. Do not merge desktop and mobile proof from different revisions into one unqualified pass.
- **State coverage versus capture count:** six named capture slots may contain identical pixels, especially for a static page. Compare the capture digests and the visible behavior, label static-equivalent frames explicitly, and report which transitions were actually exercised, which were untested, and why duplicates are expected. Do not describe six citations as six distinct visual states. Do not fail a correct static or reduced-motion state solely because its pixels match another capture; the brief determines which transitions must differ.

### Result-contract worked examples (choice-and-result briefs)

When a brief promises that a choice changes a deliverable, test the promise in the concrete domain vocabulary. A time change cannot only scale every displayed duration and rename the plan if the page promises a different workout; show a coherent change in concrete actions, sequence or dosage under an openly authored rule, or narrow the promise to "shorter version of this example." Check that every named movement has usable dose information at the level justified by the brief, rather than a large unexplained timer. Distinguish equipment and household supports honestly: if a movement needs a chair, wall, step or mat, the "none" choice cannot silently use it; either disclose the support, choose an unsupported move, or define the choice as "no exercise equipment" with the support named. A segment that stops halfway without an explicit scale, denominator or remainder suggests missing work; reconcile the quantified result to its components in the displayed state.

### Composition, behavior, and resilience cases

Dogfood the REX MCP itself when building a study: freeze the brief in a REX task, inspect the `rex_design_workflow` prompt and original skill, use the scoped `rex_next`/read/edit/run/test path for changes, and submit evidence through its custody flow. Keep a miss ledger with the failure class, exact task/tool step, rendered counterexample, why the current guardrail did not catch it and the proposed general correction. Do not claim that merely reading the prompt or passing a test means an external agent obeyed it. Do not add a new scene-specific rule when an existing class can be tested more clearly.

In a landing-page Visual brief, the first host viewport should make the object or behavior that carries the brief's evidence visible, legible and dominant in the composition on desktop and mobile; keep the primary action adjacent to it when interaction is the story. Remove decorative labels, redundant frames and explanatory furniture that compete with it. Compare the hierarchy and crop to live examples for principles, not copied layouts or brand styling. Treat a tidy card and several small effects as insufficient when the brief calls for a strong visual idea. This is a strong-composition check for landing-page Visual briefs; a quiet index, document, or multi-route interface is out of its scope and passes by making its real task, status, data and next action legible.
Do not promote a claimed visual behavior from source code, an accessibility description, a slider value, or an in-flight transition frame to a fact in the handoff. Wait until the rendered state settles, then inspect the actual host-framed pixels at the claimed endpoint. If the copy says a line continues on the other side of an occluder, point to its visible continuation; if the screenshot only shows the near side, the claim is unverified or false even if the DOM width eventually changes. Capture matching crops at 0, midpoint, 100 and reverse, with the numeric state visible where possible. Separate observed pixels from inferred mechanics and name any mismatch before reporting completion.

Before approving a continuous Visual control, define a concrete pixel-delta proof. Capture the same camera and crop at its start, midpoint and end, then reverse to start. The changed object must move or transform enough to be obvious without reading the numeric label; a slider readout or SVG attribute change alone is insufficient. If a light, shadow, object, or scene state is the promise, confirm its visible silhouette and placement change at the correct place, while the unaffected anchors stay coherent. If start and end are almost indistinguishable at actual delivery size, reject the concept or enlarge the transformation rather than giving it a passing motion grade. Inspect the mobile host frame as well as desktop; keep the visual object and the control that changes it in the same opening viewport, including the host header. If the control falls below the fold, rebalance the page or attach it to the scene, then capture both widths again. This is a visual gate, not a source-text checklist or a guarantee of taste. Record the frozen brief, image pair, values, viewport, and remaining defects in the review.


Implement responsive compositions rather than shrinking the desktop scene. Make navigation and calls to action usable with focus and reduced motion. Keep essential content visible without JavaScript or after an animation fails, and make the reduced-motion path immediate and readable. When typography carries the visual idea, test the page with the intended font blocked and with content lengthened or translated. Preserve the central composition without clipping meaning, navigation or calls to action. A font swap must not cover a control or shift a label away from its object; check the first viewport and later content at narrow and wide widths. Use real words shaped like the target content, not filler; if no translation has been reviewed, mark it as a stress test rather than claim localization quality. For finite or timed Visual motion, the reduced-motion equivalent must not flash a static end state briefly and then disappear on the animation timer: let the state remain readable until a clearly labeled user action, or hold it long enough for the content to be understood; verify the settled state after the original timer window. For a script-dependent Visual control, do not leave an inert action visible when the script never starts: render a truthful static note, hide the control by default, and reveal it only after initialization succeeds. Inspect the JS-disabled first viewport with a fresh URL or disabled cache - a stale screenshot can conceal a failed fallback - and at each breakpoint check computed visibility and rendered pixels with scripting disabled, since responsive CSS can override a script-off hidden control. Distinguish initial script failure from a later failed animation after the control was already activated. Render and inspect the opening frame, later sections, narrow and mobile crops, and actual animation playback at its start, middle, and end; for scroll choreography, scroll through it on desktop and mobile and check pinned height, overlap, focus, and exiting the scene. Render the reduced-motion path separately rather than inferring it from a CSS rule or source. Compare to references on observable traits such as image integration, type rhythm and composition; a screenshot does not prove its interactions or accessibility. Review whether the work achieves its own visual thesis before claiming taste or superiority.

A compact regression set for any responsive review: right-edge code clipping at the declared wide width, code or labels that fall below readable size at phone width, and an empty band between sections that signals no next content job. These three recur across unrelated briefs; check them at the frozen widths before polishing, alongside the reduced-motion and failure checks above.

## Interaction workflow cases

Load this section only when the work touches one of these workflows; apply the matching cases, not the whole list. The general interaction guidance - state coverage, async snapshots, provenance, review invalidation, and honest write controls - lives in `../SKILL.md`.

- **Two-dimensional tables and reflow:** for a table needing two-dimensional layout, confine horizontal scrolling to the table rather than the whole page; keep the heading, controls and text outside it reflowed, and allow individual cells to wrap. Label and focus the scroll region only when it actually overflows, show the way to hidden columns, and remove it from tab order when it does not scroll or has no data. At a 320 CSS-pixel viewport, inspect both edges and the empty state. A 320px viewport proxy is not an actual browser-zoom test. W3C Reflow guidance explains the table exception and its limit: https://www.w3.org/WAI/WCAG22/Understanding/reflow . Do not color a rise or fall good/bad unless the product meaning establishes it. Tables need scannability and useful empty states. For a dense table, keep the item identity, status, owner, and next safe step together at narrow widths; choose a card/list transformation or an explicit scoped table scroll rather than forcing the entire page sideways. Test a long title and owner, several status types, filtered and unfiltered counts, and the route back from zero matches.

- **Sequence editing:** for priority or sequence editing, move stable item IDs rather than trusting similar display names or array positions. Provide keyboard-reachable move controls and announce the new position; disable impossible directions, preserve focus on the moved item, and invalidate an earlier review after every move. Keep a local order check distinct from a saved server order, and verify the exact ordered IDs, return/reset path and narrow layout. Dragging alone is not an accessible or sufficient route.

- **Paged and cursor-based results:** scope each cursor and in-flight request to its filter and snapshot. A filter change discards old pages and ignores late responses; a failed next page retains existing rows with their earlier-page label and offers a real retry of the same view. Do not present the number shown as an overall total when the service gives no total. Test filter changes while a request is pending, last page, zero results, failure and retry at narrow width.

- **Bulk actions:** for a partial bulk result, show each item ID beside its confirmed outcome and next step; keep aggregate counts truthful, separate permission-blocked from transient failure and unknown outcome, and retry only confirmed eligible items rather than replaying a completed batch. For bulk review, bind the exact selected IDs and status labels to the displayed snapshot/version; a changed snapshot must clear or reconcile the selection and invalidate any earlier review before an action can proceed. Inspect the exact review, a data change between selection and review, and the focus path back to current records. A local demo without a backend must not offer a plausible bulk commit control.

- **Source reconciliation:** when reconciling disagreeing sources, do not merge a record by a single latest-timestamp rule. Show field-level values, source identity, revision and observation time, and keep a provisional choice separate from verified truth or a saved record. A source update invalidates selections and comparisons made against the old snapshot; re-read current evidence before any conditional write. A local comparison is not an audit trail or authority check.

- **Destructive flows:** identify the exact target ID, distinguishing details and current revision at review, not just a familiar display name. State what is deleted, who can be affected, and whether recovery is real, timed or unavailable. An in-page Undo that merely restores local state is not a service rollback. Exercise wrong-target input, cancellation/Escape, completion, the neighboring look-alike record and the return path; do not invent an active Delete control in a disconnected study.

- **Approvals and quotes:** for approvals, quotes or other consequential decisions, bind a check to the exact amount, record and source revision. If the value or revision changes, invalidate the old check, show what changed and require fresh review. A green local check is not the person's approval, a service acceptance or permission to commit money. Do not put a plausible Pay or Approve control on a disconnected example.

- **Offline and queued work:** separate editor draft, device-local queue, network dispatch, unknown outcome and service receipt. Do not label a local queue entry Sent or imply another person received it. Disclose storage durability across reload and device changes; keep the draft and operation identity while reconciling a lost response, and do not automatically replay a write on reconnect unless the service supplies conclusive status or enforced idempotency. Simulated reconnect cannot prove delivery.

- **Sensitive record details:** for a screen with sensitive record details, default to the least revealing view that still lets the person choose the right item. Reveal one field at a time with a keyboard-operable control whose name says which item and whether it will show or hide the value. Do not make masking a false security claim: the data may still be in page source, browser history, screenshots or network responses. On item switch, navigation, timeout or permission loss, hide values and invalidate any prior review; a copied value remains outside the page's control. Test two similar records, reveal/hide, keyboard action, focus, narrow layout and stale review. A local mask is not a service authorization or data-leak prevention proof.

- **Multi-account actions:** show the selected sending or owning account at the point of review, not only in a global menu. Bind any local review to the exact account, destination and draft version. Switching account must invalidate that review, clear account-specific contacts and permissions, and preserve user-entered draft text separately until its new account and recipient are checked. A familiar recipient name in another account is not evidence of the same address or audience. Inspect a late lookup from the prior account, switch back, and verify which draft and recipient are active; a local preview is neither an authorization nor a sent item.

- **Import previews and spreadsheet exports:** for an import preview, keep raw source values, row numbers and parsed interpretations together. Flag ambiguous headers, duplicate identifiers, invalid units and partial rows before offering any commit. A recorded zero is data, not a missing value. Invalidate an earlier preview when source content changes and show both valid and rejected counts from the same current source. For actual files use a format-aware parser rather than silently splitting quoted CSV on commas. A local parser cannot claim service acceptance or live destination matching; without a backend, stop at review rather than a plausible Import button. When a workflow exports untrusted values to a spreadsheet, treat cell content as data, not trusted markup or formulas. Check formula-leading characters after parsing and serialization, including separators, quotes and control characters that can move a value to a new cell; a neat preview is not proof the downloaded file will remain safe when opened or re-saved. Verify the actual exported bytes and opening behavior in target spreadsheet software, and never call a local display-only check a secure export. See OWASP CSV Injection: https://owasp.org/www-community/attacks/CSV_Injection .

- **Collaborative and optimistic writes:** a successful local check on revision A is stale when revision B arrives: preserve the unsaved draft, show both versions and the base/current revisions, and block a plausible save or success state until the conflict is resolved against the latest revision. If a Copy newer text action replaces the editor contents, preserve a reversible route back to the previous draft and its base revision; a visible comparison that disappears after copying is not draft recovery. Distinguish in-page undo from durable persistence across reloads. Do not move focus out of an editor on every keystroke just to announce changed status. A preview or local check cannot replace a server-side conditional write. For optimistic state changes, distinguish requested or pending from service-confirmed values; a pending write must not wear a success badge. On explicit rejection, restore or reconcile the displayed item without losing the person’s input and explain the next step. If a response is lost, classify the outcome as unknown, not rejected, and check the operation before retry.

- **Settings, permissions and dependent controls:** settings pages need an honest distinction between current saved values, unsaved edits, a preview and a local check. For access or permission settings, compute the effective result from every applicable cap and explicit rule instead of presenting the edited role toggle alone; show which rule limits access. A draft check cannot establish live entitlement. Invalidate the check on any input change and never imply that an over-broad draft passed a permission test. For dependent controls, test each branch: hide or disable fields that no longer apply, clear irrelevant errors, retain values only when that helps recovery, and restore a sensible focus target. A passing local check must be invalidated when values change; if no save service exists, do not offer a plausible Save button. Put the task before an optional preview on narrow screens unless a task-grounded reason reverses that order.

- **Time-zone instants:** for a task interface that converts a local date and time to an instant, check time-zone rules rather than assuming a wall-clock label is unique. A fall-back hour can occur twice with different offsets; a spring-forward hour may not exist. Show the zone, offset and equivalent instant, block ambiguous or nonexistent entries before a consequential action, and seek the request author's actual choice rather than auto-picking an offset. A local comparison does not authorize an event or notification.

- **Session expiry during a draft or review:** preserve the text and mark the check stale; never describe renewed access as a completed write or automatically replay an uncertain request. Give the person a safe route to copy or revisit the draft, and distinguish what survives an in-page return from reload/device recovery. A local mock cannot prove sign-in, access restoration, or service outcome. Test expiry after a check, editing while blocked, return with input intact and a fresh check; inspect narrow pixels.

- **Branching multi-step work:** reveal only the active branch, keep inactive values only as recoverable draft data, and clear irrelevant errors and checks when the branch changes. Bind a local review to the exact branch and values; back navigation may preserve input but an edited draft must invalidate the earlier check. Show whether the review is local, saved or delivered, and never leave a plausible Send action in a disconnected example. Test an invalid active field, change branches after review, switch back, and inspect the final current review at narrow width. Multi-step flows need progress and a way back.
