# REX Design

Choose the right job for the prompt before designing. Visual mode makes a distinctive, high-quality visual experience; Production mode makes a dependable task interface. Neither mode permits invented claims, inaccessible controls, or a static render mislabeled as live behavior. Start from the existing product and code, not a generic visual trend. The method is a short conversation with the work, not a stack of mandatory checklists: frame the visitor's useful change and the truthful material that makes it visible; for consequential new design, explore two structural ways to show it; choose a brief-specific craft system; implement honest behavior; then walk the actual pixels and actions as a first-time visitor and revise with KEEP / CHANGE / CUT, preserving what works. If no evidence supports a claim, mark the unknown rather than manufacture a result.

## Route the prompt: Visual or Production

Read the full prompt and identify its *intended outcome*, not just a keyword. Choose one mode before writing code and state the reason in the review record: explicitly record **Visual** or **Production** and why, from the primary intended outcome, before any styling. Explicit audience, functional constraints, and real product requirements override a generic request for polish. If the brief names a launch, campaign, portfolio, editorial story, showcase, striking hero, art direction, cinematic motion, or a visually ambitious concept, choose **Visual** even when it also says "page" or "dashboard". If the brief asks people to complete a real workflow, inspect data, configure a product, recover from errors, or use a page in production, choose **Production** even if it asks to look good. A request can be ambitious because of its business scope or number of features without being visually ambitious: do not route it to Visual for size alone. When both are present, preserve hard functional requirements, then use Visual only if visual impact is explicitly the primary success criterion; otherwise use Production. If neither is clear, default to Production and record the assumption. Ask only if a wrong choice changes the purpose or audience and the prompt cannot resolve it.

Visual is not a shortcut around production basics, and Production is not a ban on original art direction. Mode changes where design effort and review attention concentrate, not whether accessibility and honest state behavior matter. Do not call a mode a quality rating. Neither mode requires motion or a central interaction without a task-based reason: a quiet index, a document, a dashboard with several routes, or an existing UI that must stay recognizable can pass by making its real task, navigation, artifact or known limitation clear.

## Fast execution path

Use this as a route through the detailed guidance, not as another checklist or a requirement to create duplicate artifacts. Keep one concise [review record](#one-review-record-conditional-sections); select the gates that fit the task, and mark untested states honestly.

1. **Frame the brief:** identify the audience, task or intended experience, constraints, supplied evidence, unknowns, and next action. Inspect existing routes, assets, tokens, and working flows before proposing a redesign. See [Brief and audit](#brief-and-audit).
2. **Route the prompt:** explicitly choose Visual or Production from the person's primary success criterion and record why; do not infer mode from page size or the word "polish".
3. **Explore and choose at concept scale:** for a new page, primary workflow, major redesign, or change to the visual thesis, run the [pre-build concept gate](#pre-build-concept-gate) with two structurally different directions on the same evidence. For a narrow UI correction - one component or state, with the existing experience as the baseline - test the affected task, state, and nearby layout; any change to the first view, information hierarchy, or promised outcome forces the full gate, and a small change that alters accessibility or a consequential state likewise expands the review. For critique-only work, assess the delivered experience without inventing replacement concepts unless asked. Every scope still checks changed behavior and rendered results while preserving truth and accessibility. Use the result-contract check in [landing-page craft](#landing-page-craft-from-observed-pages) when the brief promises choices or outcomes, and load the [targeted visual failure cases](#targeted-visual-failure-cases) only when their trigger applies.
4. **Choose the system and build:** map the promised interaction and recovery states; if the experience is static, do not add controls for novelty. Choose a [craft system](#choose-a-craft-system) for the brief, then implement with the [Visual](#visual-mode-an-art-directed-experience) or [Production](#production-mode-dependable-pages) guidance. Freeze the supported width range before the first visual check - it cannot be narrowed after seeing a failure ([Implement and verify](#implement-and-verify)) - then render the real host frame across that frozen range at settled states; exercise the primary path plus applicable divergent, failure, keyboard, and reduced-motion states. Compare pixels, not just source code or capture counts.
5. **Walk, revise, and hand off:** walk the actual pixels and actions as a first-time visitor on desktop and phone; critique with KEEP / CHANGE / CUT and make targeted revisions that preserve what works. Handoff evidence, not confidence: the direction and tradeoff, changed files, rendered paths and states actually checked, and remaining assumptions or defects. See [Evidence and review](#evidence-and-review) and [Handoff](#handoff).

## One review record, conditional sections

Keep one review record per piece of work. It is a single document with conditional sections, not six separate deliverables; write a section only when its trigger fires, and for each skipped section quote the trigger that fails to fire. A narrow patch that adds no promised result and no new consequential state may need only A and F.

- **A. Brief (all work):** the route, Visual or Production, and the reason; the visitor and their task or intended experience; the action or success measure; constraints; source-backed facts and their status; explicit unknowns; and the current UI baseline when one exists.
- **B. Concept (new page, primary workflow, major redesign, or change of visual thesis):** two structurally different directions on the same evidence, shown as delivery-size desktop and short-phone crops; the selected direction, the rejected direction, and the specific reason it lost. Outside this trigger, record the baseline and the affected scope instead.
- **C. Claim and consequence (only when the work promises a result, data relation, visual mapping, decision, or interactive change):** the source or authoring status of each claim; the input-to-output rule; divergent and failure states; and the final readback. Safety-sensitive claims carry their exact scope and limits beside the result.
- **D. State matrix (Production work and any relevant interactive workflow whose changed behavior spans more than one consequential state):** one row per such state, using the [state coverage ledger](#state-coverage-ledger) columns. Mark a state not applicable only with a reason.
- **E. Craft (any design or redesign):** the chosen craft-system values with their brief-specific rationale, per [Choose a craft system](#choose-a-craft-system), plus the supported width range and writing scripts.
- **F. Review (every changed rendered UI):** revision and capture metadata; the states and widths inspected; the first scan and first-time walk where relevant; KEEP / CHANGE / CUT or an explicit no-change; before/after pixel and action readbacks for each fix; and unresolved risk.

Freeze the brief, the supported width range, and the success criteria before review; never narrow them after seeing a failure.

## Landing-page craft from observed pages

The reference study is a range of 101 distinct company-produced sites across software, hardware, retail, culture, publishing, public service and finance, inspected in desktop and phone views with recorded loading/overlay limits. These are observed pages, not proof of the designers' identities or of conversion performance. Use the original brief and the product's own material, not any site's layout, campaign asset, brand color, headline or animation. The study's source ledger stays private; examples below are evidence of a *mechanism*, not templates to implement.

Lead with the visitor and their action. Choose what the person came to do: a transaction can put the working task first (Wise's converter, Delta's flight search); an editorial site can put one specific story and its provenance first (NPR, The Guardian); a physical product can put the real object and its material behavior first (Converse, Leica, Tiffany); a complex service can offer a question and distinct routes (IBM, Dell). Huly, Tesla and Codex are different answers to different jobs. Then write a compact **content and evidence map**: the audience and first decision; the specific object, story or task that can carry the first view; the source and status of each claim and visual - source-backed or explicitly illustrative; the next action that actually exists; and what the next chapter adds. A proof object is one candidate evidence form, never a compulsory hero or animated widget: do not require an input/output widget, cinematic photo, logo wall or two buttons of every page, and a multi-task interface needs no single focal object to pass. An editorial or object-led hero is free to avoid a widget, but it cannot quietly replace a requested choice-and-result product with a mood image or slogan. If real assets or product behavior are unavailable, say what is illustrative and make an honest authored example rather than a fabricated product screenshot. A static composition is valid when interaction has no job. In an established product, inspect its existing assets, voice and flows before replacing them.

First pass the brief's **result contract** before any taste or ownable-proof test. The executable sequence: list every promised input with its source-backed or openly authored rule and the concrete deliverable a person can actually use; show a legible example of that deliverable and a second divergent state; write the promised effect of each axis, then change one axis at a time while holding the others fixed; reconcile every displayed quantity to its components; and only then let art direction compete for space. An input echo, mood line, decorative symbol, unexplained timer or generic status is not a result. If the brief asks for several independent choices, keep each one a legible choice and show how each affects the result; a preselected example or pagination through presets is not equivalent. If a choice only rescales the displayed values and renames the plan while the page promises a different deliverable, it fails; show a coherent change in concrete actions, sequence or dosage under an openly authored rule, or narrow the promise. Distinguish required supports honestly: a "none required" choice cannot silently rely on an undisclosed support; disclose the support, choose an unsupported option, or redefine the choice with the support named. Inspect the whole result panel at delivery size: large unused space around tiny outputs is missing proof, not restraint. Compare two choices by their usable contents, not only by a changed total or bar length. If the promised deliverable cannot be sourced, make its limits explicit and use a truthful worked example or stop the concept; never invent a prescription or live operation. Treat an attractive but unexplained composition as a failed concept, not a nearly finished page: before final polish, hand a reader the first-view crop with the headline hidden and ask them to recover the useful result, its units or component amounts, and the next action. If those cannot be found at legible size, take area back from the stage, decoration or setup instead of adding more explanatory copy. The worked exercise examples that developed this contract are failure cases in [Visual review cases](references/visual-review-cases.md).

When a full concept comparison is warranted and the brief claims a focal proof, test the **ownable proof** of the two strongest structural directions with a single focal-proof budget, not an added layout template. The executable sequence: name the proof material and its truthful change; mark the first-scan subject with its source, receiver and consequence; feasibility-mock cause-and-effect claims at delivery size; then record which concept lost and what the winning focal area actually proves. The proof material is one real or explicitly illustrative material, object or work record from this product, with the viewer's useful inference. Check how much of the visible area the subject needs to be recognized, and whether the next safe decision or route still reads without explanatory copy. The feasibility mock is a rough same-crop sketch at desktop and 390×650 showing the source, affected object or receiver, and visible effect in both settled states, captions hidden; if the effect cannot be seen reaching its named receiver at legible size, change the visual thesis or narrow the claim instead of counting a label or diagram arrow as proof. Reject a concept whose decorative device, multiple small cards, or oversized blank field takes the focal area while the actual payoff becomes tiny, disjoint or clipped, and a physically impressive scene whose claimed consequence does not meet its receiver in settled pixels. This is a pre-build comparison, not a required full-bleed photo, centered title, fixed percentage, or taste score: whitespace can work when the actual product asset or brand carries meaning, but it does not create missing proof for a fictional brief. Do not enlarge a thin fabricated UI or physical diagram to imply a real product asset. Cover the brand and delete the headline: if the hero is still just a familiar split, cards, pill controls or a generic progress dial that could sell an unrelated product, keep the content contract and redesign the visual thesis, not merely the colors. A signature visual for a choice-and-result product must carry the useful result data itself, not merely surround it. For a state change, hold unaffected parts of the scene steady and make the actual effect visible at the object and its receiver, not only in a label or button. Do not depict a fictional product as a real photograph or fabricate an unverified capability to win the taste test. A quiet index, document, dashboard with several routes, or an existing UI that must stay recognizable claims no focal proof: it passes by making its real task, navigation, artifact or known limitation clear, and no single focal object is required. Inspect the chosen concept in final pixels.

Make the first view a deliberate editorial cut, not a prescribed anatomy. A strong product photograph can be proof of form and material without exposing the product's algorithm. A real UI may be proof when it is legible and representative. A terse story with an immediately visible evidence image can establish an editorial premise. The title, object and route should work together, but the relative weight depends on the job. Ask what a viewer can recognize in one scan, and whether the copy adds a specific fact rather than explaining a generic graphic. Restraint, typography, crop and negative space are decisions with opportunity costs, not a palette to apply. Avoid proxy excitement from gradients, floating blobs, pills, fake dashboards and meaningless motion.

**Recompose for phone.** Check a short 390×650 frame with real header/host height and a settled full-size view. Preserve the subject, readable claim and honest route by changing sequence, crop and density, not merely scaling desktop. Tiffany changes its photographic crop and text order; Kickstarter stacks discovery and the named project; IBM removes the secondary news rail. A first-view crop may show only a purposeful glimpse of the next chapter, but must not conceal the primary mechanism or control with its legible effect, the only meaningful action, or a limitation essential to the claim. For a brief whose point is changing the result, place the primary control and its effect together inside the actual host-framed 390×650 opening; a heading or the start of a result at the bottom edge does not count. If the subject or effect is clipped, reframe or change the sequence; do not rescue the crop by shrinking labels, controls or the subject below useful size. When several facts cannot fit legibly together, provide a readable summary and an obvious route to full detail instead of compressing an entire desktop chain into miniature phone type. Test an overlay, slow media and no-media state: many surveyed pages lost their phone hierarchy to cookie/signup dialogs or lazy assets. Do not mistake those failures for craft.

Give subsequent sections distinct evidence jobs. A hero can set an object or premise; the next chapter may show use, choice, mechanism, inventory, origin, a real example, an objection or a limitation. Converse shifts from model portrait to weather detail; Kickstarter names a creator and project state; Canon moves from camera to deals and learning. Trace each factual detail in later sections to the brief or a checked source, including named channels, timestamps, logs, measurements and provenance. An "example data" label does not license invented specifics that look like observed records; either obtain the source, use clearly authored hypothetical placeholders without implying observation, or omit the detail. A sparse brief may not supply a SKU, order-line identity or decision rule; mark that missing source in the review and narrow the visible claim rather than fabricate the record or recommendation to satisfy a visual proof test. After truth is secure, inspect whether the first view names and shows the subject's concrete action or object, not an abstract category, unlabeled schematic or generic admin box. Do not let a later section claim that a choice changes movements, receiving surfaces or a decision record unless those differences exist in the rendered divergent states. The next chapter must add a specific visual consequence or usable mechanism if the page promises one, not a table or diagram that merely narrates the hero; otherwise cut it. If later cards simply restate the first promise, cut them. Compare this version with the last truthful baseline at identical desktop and short-phone crops, and retain the baseline if the revision only becomes more literal without more product-specific proof. Use motion only when it changes understanding, guides attention or shows a true state change; inspect resting, moving, reduced-motion and failure states when motion is used. A page can be quietly static and excellent.

When a brief includes a human decision, show the actual distinct choices as visible, honest, comparable controls; a sentence saying "approve or reject" is not two paths. Do not style one as a real enabled action while the other is merely decorative or disabled unless the product state explains why. Audit every directional mark and record label before handoff. An arrow means a real direction, transfer or transformation, not merely two values that disagree; show independent source claims as a comparison without a false flow. Do not call a schematic or authored example a "source line" or record if the brief gives only quantities and no retrievable line identity. If the experience is only an illustrative preview, label the controls and their outcome as examples rather than live writes. Give both permitted decisions comparable visual weight and legible keyboard-reachable labels; a solid primary action against a faint outline can bias a safety review even when both controls technically exist. Show the exact record identifier, the source and proposed values **with units**, and the direction of the proposed change in one sentence beside the decision (for example, "Change order 418 from 12 units to 10 units"). Use the actual source's vocabulary; do not turn a warehouse count into an unsupported shelf claim. Make provenance visible in the composition when it determines trust, rather than hiding it in a tiny caption below the numbers. For an exception decision, the distinctive visual should be the actual comparison and custody of the discrepancy: keep independently sourced values, their supplied identifiers and observation limits readable together; show the proposed change as a separate human decision, then retain the rejected proposal as history without implying an order write. If the brief supplies no retrievable line ID, timestamp or audit service, present a clearly illustrative comparison and do not manufacture an audit trail. Test the version with buttons and brand hidden: the evidence and decision boundary should still be recognizable as this product's work, not a generic form card. If a later section walks through the same example, it must reveal new evidence, an edge case or a real next step, not repeat the hero at larger size. At short-phone size, keep the illustrative-status label and what each human choice means readable in the same visible decision area; if they fall below the fold, recompose instead of shrinking captions. Treat a proposal as a separate, uncommitted object until a real approval or service receipt changes it: put its origin, proposed effect and decision boundary together, and in the rejected state retain the proposal only as unapplied history. Hide the brand and inspect first-view and settled-state crops with a reader: can they identify which value was observed, who or what proposed the change, what approving would affect, and whether anything was actually changed? A beautiful before/after infographic with ambiguous custody or an active-looking rejected proposal fails this job.

After the primary action, run a **settled-state consistency audit** on the actual end pixels, not on code or the creator's intended state. Enumerate every visible status badge, selected and unselected control label, accessible name, proposal/value, caption and claimed receiver or work object; compare each with the action's outcome and the original source facts. Keep option names stable as choices; put a "current value" prefix only in a live summary that changes with selection. Test divergent choices and reversal, reading all options each time: an unselected option must not still sound like the current value. If a rejected review still says "needs a decision", shows an actionable proposal or leaves both decision buttons active, the page contradicts its own state. For any result that claims a quantity, duration, allocation or dose, reconcile the displayed total to its component rows, units and omissions in every divergent state; show the rule or state the limit. If a bar, ring or segment graphic stands for those components, each meaningful part needs a readable identity and amount in the same view; otherwise it is decoration and should yield its space to the actual result. A shorter workout that changes only a label or drops a row without accounting for its sets and minutes is not a 10-minute plan. If a shorter workout still marks 20 minutes selected or repeats the same movement/time plan while promising adaptation, its result contradicts the controls. If a lamp caption says light reaches a page or wall but the visible light footprint misses that surface, the pixels contradict the claim. These are examples of one failure class, not mandatory scene recipes. For a claimed physical cause and effect, the settled-state geometry audit is required before handoff: in actual same-crop start, intermediate, end and reverse pixels, trace the emitter or source, its direction/path, the named receiving surface and visible footprint. The receiving patch must sit inside the source-derived footprint in the settled frame, with a legible boundary or falloff on the actual receiving plane; a bright shape partly outside its own beam, a clipped wedge substituted for a surface, or an occluder that does not interrupt the path is a mismatch even when some light touches the named object. If they fail to meet in any claimed state, repair and recapture or narrow the claim; a gate pass, caption or model-coordinate note is not evidence of contact. Repair the underlying state/geometry and copy together; do not hide the conflict under a disclaimer, change only the caption, or call a text-gate pass proof of causal truth. Reinspect the same-crop start/end/reverse and recapture all cited evidence from one final source revision.

Before handing off, inspect settled desktop, short phone and a later chapter as pixels. Include the second settled state in the handoff for a page that claims adaptation; if only the default state was captured, report the mechanism unverified rather than inferring it from code or controls. Hide the brand name and ask whether the content, crop, type rhythm and action still tell *this* product's story. Inspect the same widths against the prior build and record taste, task clarity and phone integrity as separate informal diagnostics for spotting regressions - useful signals, never passing evidence; a clearer mechanism can still look worse. Record one substantive weakness and its correction, plus any missing assets or states. Do not report compliance with a checklist as evidence of human-level quality.

## Pre-build concept gate

Choose the gate by the size and consequence of the change. For Production or multi-route work, the first-view and visual-language tests below apply to task legibility - status, data and next action - not to focal-subject art direction. Use a full concept comparison for a new page, primary workflow, major redesign, or change to the product's visual thesis. Any change to the first view, information hierarchy, or promised outcome forces the full gate. Narrow means one component or state, with the existing experience as the baseline: test the affected task, state, and nearby layout; a second page-wide concept adds noise rather than evidence. For critique-only work, assess the delivered experience and report gaps without drafting replacement concepts unless asked. A small change that alters accessibility or a consequential state likewise expands the review beyond the touched component. In every scope, test the changed behavior and rendered result; scope changes effort, not truth or accessibility requirements, and the declared scope carries into the handoff. The candidate-comparison studies below apply only when a full comparison is warranted; their scope does not waive truth, accessibility, or rendered-result checks.

### Concept and proof

For work that needs a full concept comparison, compare at least **two structurally different concepts** from the frozen brief: structurally different means different organizing ideas (for example, object-led versus task-led), not two skins of the same hero, and the choice is made by the brief's evidence, audience and delivery frame. Add more candidates only when uncertainty warrants them, not surface treatments of the same interaction. If neither direction has enough real material, seek it or narrow the claim. For each, write the core user-visible claim, the subject-specific rule or content that makes it true, the starting state, the meaningful action or progression if any, and the resulting payoff. Compare the concepts without styling: remove type, color, motion, and explanatory labels, then describe what a person would learn, do, or see change. If the payoff is only a generic symbol, a repeated line, or an invented fact presented as a discovery, reject it before implementation. Do not add interactivity when a static page serves the brief better.

When a full concept comparison is warranted, make that comparison visible before polishing: assemble a one-screen, side-by-side first-view study of the two strongest **structurally different** ideas, using the same honest product evidence and real words. Include both desktop and short-phone crops at delivery size, not two descriptions or the same card layout in different colors. Hide the brand and headline. Point to the useful relation, object or consequence a viewer can still read in each crop, then choose one and record the specific reason the other lost. A missing product asset is a reason to narrow the concept, not to dress a generic card as evidence. This study is a judgment aid, not an automatic taste gate; if neither reads, revise before writing the polished page.

For a candidate that promises to reveal a relation, apply a **relationship-proof baseline** before layout or visual polish. Name the exact source-backed relation that its spatial or temporal behavior makes legible, and put the real words and marks at their intended relative positions in a stripped desktop and 390×650 sketch. Compare it in one scan against a well-typeset plain list, diff, map or node-link view of the same source. Can the viewer notice a task-relevant relation or consequence faster and more accurately, without reading a headline or legend to compensate? If not, reject the candidate before code, even when it is clear and honest. A container around a graph, a decorated diff or an editorial headline is not a new relationship. Keep every relation source-traceable and unknowns visible; this gate does not permit invented data or an inferred edge styled as fact. Record the baseline and rejection reason in the review.

Apply a **claim/content contract test** to every finalist. Quote the exact source fact or state that entails each reveal and show how the reveal changes the reading of another part of the content or the user's next decision. Distinguish interpretation from fact, and authored fiction from discovery; label fiction honestly if the brief permits it. If a concept depends on missing content, request or research that content rather than designing around a placeholder. For Production, test the proposed outcome against real data, permissions, and service states rather than a plausible local mock. Keep the candidate ideas and rejection reasons in the review record, choose a survivor for its actual payoff, and stop to revise the concept or brief when none survive. This is a pre-build decision, not a promise that the finished pixels or behavior will pass review.

Before a data-led concept survives, sketch its **delivery-size proof** alongside the no-visuals test: at the actual first viewport on desktop and a short mobile screen, identify the focal mark, its minimum readable size, the needed legend/source/uncertainty, and what must be visible together. Do not confuse verified data provenance with a compelling visual idea. A fine-line map that only reads after zoom or a citation that falls below the fold fails the concept at that size, even when its facts and geometry are correct. Recompose the idea or choose a different medium rather than squeezing source notes into tiny type. Verify these projected constraints in rendered pixels after implementation; a sketch cannot certify readability.

### First view and phone

At the actual desktop first view and 390×650 short-mobile view, the brief's subject, evidence or interaction must be immediately legible. A headline may carry the premise when the words are the content, but it should not push the only proof or next route out of reach. Remove explanatory copy temporarily: can someone still locate the focal evidence, its state and the next meaningful action? Reject the composition if a headline or explainer owns the first view while a small widget, map, receipt or interaction carries the real work. Do not fix this by deleting necessary provenance, uncertainty or recovery; enlarge and recompose the evidence so those remain readable together. Compare the settled pixels in both viewports, including the surrounding host, before approving. For a claim that depends on two or more related states, marks or receipts, sketch and inspect all endpoints plus their join inside the *visible* host-framed first viewport. Do not count an endpoint below the fold, behind a tab, or readable only in a full-page capture as a one-scan pass; compare the same cropped frame with the plain baseline before implementation and again after rendering. If the relation cannot fit at legible size, simplify the composition or stop the concept rather than hiding an endpoint.

A brief such as "make a landing page for an app" names a category, not a brand system or a product screenshot. Before choosing a hero composition, state the intended person, their first decision, the one defensible product promise, and which facts/assets are *not* supplied. If the product is fictional, label it; write illustrative UI and claims as examples, not as live metrics, store availability or measured outcomes. Do not fill an empty brief by stacking the familiar anatomy: pill-shaped category eyebrow, one differently colored headline word, two equal hero CTAs, a generic phone silhouette, invented streak/readiness numbers, and three interchangeable feature cards. These are symptoms, not prohibited components. Keep a component only if its content and placement make a specific decision clearer than the plain version.

For each pre-build candidate, put the **product's own evidence** in the first host-framed viewport: this may be an actual object, a representative use scene, a live task, a real product interface, or an honest worked example. Show an input, decision or consequence when the brief promises one; do not impose a compulsory widget on an object-, story- or catalog-led page. A quiet index or multi-route interface needs no single focal evidence object: its legible status, data and next action are the first-view evidence. When a product claims to generate an outcome from inputs, identify the exact input dimensions, the mapping (verified or explicitly authored) and the usable result before choosing the visual form. Keep the input labels, selected values, result and reason findable together without hiding required dimensions behind a carousel, faux selection or explanatory section. A product's promise is not fulfilled by restating a selected value in larger type. Sketch the actual 390×650 crop with navigation and any host header *before* choosing type, asset or animation. Name what the user could infer if all marketing copy were hidden. If the purported proof lives only below the phone fold or the hero art is an empty prop, reject or recompose the candidate. A photograph can be stronger than a fabricated interface; a real product screenshot can be stronger than a photograph. Do not invent an interface and present it as real merely to satisfy a visual-asset quota.

A mobile first view does not pass because a card header or the top of an output is visible. Before implementation, draw the actual 390×650 viewport with navigation and host chrome at their real heights. Outline the **payoff bundle**: each required input dimension and its selected value when the brief promises a choice, a legible usable result with its reason or evidence, and an honest next action or limitation. If there are no required inputs, use the actual subject, evidence and route instead. Where all supporting detail cannot fit, keep a meaningful result summary and the mechanism/effect legible in the opening, with an explicit route to fuller detail below; do not shrink essential text or controls to manufacture a fit. A phone view that shows an option label but clips the consequence or hides another required control fails. Mark each bundle element's bottom edge. If the result title fits but its reason, useful details or next route are clipped, the first view fails. Recompose the page around that bundle: shorten the header and setup, reduce the number of choices, remove repeated explanation, or move secondary detail below the fold while preserving the essential reason. Never solve it by shrinking type or touch targets. After rendering, inspect the same cropped, host-framed first view in at least two divergent input states and after reversal, not a full-page screenshot. A result that only becomes understandable after scrolling is a mobile regression even if its desktop taste improves.

Write a one-sentence **audience register** before choosing display type, casing, saturation, imagery or motion: who is reading, what they may fear or hope, and what the page should sound like to them. Compare two materially different first-view treatments in grayscale, with the exact same words, for fit with that person. Subject material is only a lead, not a mandate: a workout product for beginners need not use the visual language of an aggressive gym poster. Check the final copy as well as its styling. A loud, condensed all-caps headline or an extreme name can make gentle onboarding feel like a dare. Keep intensity only when the brief, audience and actual product voice support it.

When showing an illustrative result in a safety- or suitability-sensitive area such as exercise, distinguish the known product behavior from a made-up prescription. Exact reps, rest intervals, diagnoses or personal recommendations require supplied rules and an appropriate scope. If those are absent, show an explicitly authored example or the choice-to-outcome structure without implying that the page knows what is right for this person. Place the example/limitation label beside the result, not only in a footer. Later sections must add evidence or answer an objection rather than repeat the first-view explanation.

### Visual language and chapters

Run a **template-substitution test** before polishing: swap the brand and category words with an unrelated product. If the focal visual, section order, and meaning of the primary action still work unchanged, the page has not earned its design. Replace the generic visual with a truthful product-specific example, change the section's job, or state that the brief lacks the content for a convincing product demo. Test with the rendered desktop and short-mobile opening, not just a written rationale. Choose the typeface and hierarchy for the audience and subject; a system font is acceptable when it fits, but using the browser default because no typographic decision was made is not art direction. Avoid downloading a font when licensing or network access is unclear; keep a tested fallback. One honest route to the next action beats a pair of decorative CTAs; if the product cannot be downloaded, do not label a dead button "Download". At handoff, compare the new page against a frozen generic baseline at the same widths: list the exact template symptoms removed, the subject-specific evidence visible in the first viewport, the remaining generic areas and any unequal delivery conditions. A host's checklist pass or REX's six capture slots does not establish taste. If the first view still reads as a logo/headline/empty phone/CTA arrangement, call it a failed study rather than a design win.

A signature visual device must explain the product's decision, not merely make the input look memorable. Before adding an orbit, ring, progress arc, connecting line or animated mark, write an **input-to-mark ledger**: what known or openly authored rule maps each input to the mark, what part of the mark changes for two divergent choices, and what a viewer can infer from that change without reading a headline. If the same visual survives an input change with only a number or accent swapped, treat it as decoration. Either give it a truthful causal job (for example, a segment map where the allocation actually changes) or remove it. Do not assign an invented scientific rationale to a fictional rule to rescue the device. Test the first and changed states side by side at desktop and 390×650, then reverse the choice; the source and result must stay in agreement. **Deliver that comparison in the review evidence**, not only in the implementation: record the exact input values, the two settled frames at the same crop, and the visible part of the result that differs. A six-slot capture set may contain duplicates, and a scroll film of one initial state does not show that the promised mechanism adapts. If the page is static or the brief has no truthful second state, say so rather than staging an invented change.

When the page claims a choice produces a result, its first-view sentence must name a **concrete consequence** of the choice, not a mood slogan, selected-option echo or category label. State what changed in the authored example or verified product behavior and why, at the level the source supports. Test two divergent combinations of all promised inputs: can someone compare the actual deliverable (for example, different exercise examples, a corrected order line, or a changed light direction) without relying on color, slogans or a numerical badge alone? If the source lacks a rule for a real personalized output, label a useful worked example beside its result and keep the promised controls honest rather than implying a functioning recommendation engine. Do not invent reps, rest, health suitability or personalization when the brief supplies no decision rule. Next to that result, make the route legible in words: "Explore the example" is a route to more illustrative detail, while a bare diagonal arrow is not a next step. Do not offer download, enrollment or an operating recommendation the page cannot fulfill. If the user has to scroll to discover what the result means, revisit the short-phone payoff bundle rather than adding a detached explainer.

For every below-fold section, write the new question it answers. When the first view shows a choice or adjustable object, prefer a second *divergent, source-backed state* with the changed consequence in the next chapter over a larger repeat of the hero. If the next chapter cannot add that proof, use a new limitation, source or objection instead; do not invent a second output just to fill a section. Hide its heading and compare its content with the first-view choice/result. If it repeats the same inputs, promise or explanation, cut it; do not count a different layout as new evidence. A shorter honest page is better than a long sequence of renamed summaries. For an embedded phone view, reserve host-header height and ensure the mechanism, key outcome and next safe route remain legible together; if a dense questionnaire squeezes options to small touch targets, use fewer choices, progressive disclosure or a different evidence form instead of shrinking type.

A product-specific input/output in the hero can still be a generic quiz in a new color. For a thin consumer brief, compare plausible evidence forms before selecting a candidate: an authored editorial or photographic story, an honest worked example, and an interaction only when a real response rule is available. Some briefs have just one truthful form. A mock recommendation is not an app. If using an illustrative UI, place its "example, not the app" status next to the exact result and carry that status through the next section; do not make a polished simulated interface imply working personalization. For each choice a visitor can change, write down the source-backed or openly authored mapping to its result, try divergent inputs and reverse them. If every path yields the same generic encouragement or cosmetic change, remove the control and show a truthful static example. A headline that could be printed on any wellness, finance or productivity site is not a product consequence.

Before choosing accent colors, cards or decorative marks, make a **visual-language sheet** with the subject's physical or conceptual material, a governing shape or rhythm, a typographic contrast and one color relationship. Show where each appears in the hero and at least one later section, and why each belongs to this product rather than to a current web trend. Compare at least two materially different directions in grayscale and at actual first-view sizes; only then add color. Reject a loud stripe, lime result block, pale-tint section or default display font if it merely supplies excitement to an otherwise conventional card. This is not a required palette, font or shape: a quiet neutral system may be best, and a vivid palette can work when it earns a subject-specific job. Verify contrast, licensing, fallback and mobile size in pixels.

Give each section a **different job** in a short page map: prove one claim, show a consequence or limitation the hero could not, answer an objection, or provide an honest next step. Hide the headings and compare the actual content. If a later section restates the hero's inputs as steps or wraps the same output in another card, cut it or bring genuinely new evidence. Do not stretch a one-view idea into repeated marketing sections just to look like a full landing page.

Run a **taste adversary** on the settled desktop/mobile captures and one below-fold crop. Compare the selected first view to a plain, well-typeset data-first composition carrying the same facts and actions: does its signature visual make a product-specific relation easier to see or make the subject more recognizable without relying on a brand label? If it only restyles the same cards or delays the useful evidence, remove the device rather than decorate it further. Ask: can a different brand inherit the colors, card layout, type and section rhythm unchanged; does the imagined product feel more real than the evidence warrants; does the product-specific object or outcome command attention without an oversized slogan; is the final state more distinctive than the initial one? Do not accept a clean cause-and-effect audit as the taste thesis. With the facts held fixed, compare at least one visibly different composition (page scale, section rhythm, crop, type hierarchy or product material) to the repaired baseline at desktop and short phone; keep the one whose subject and payoff read more distinctly without weakening truth or the mobile route. The adversary compares actual settled captures, not intentions: use the same host-framed crops for both arms - the compared variants of a comparative validation - and ask an independent critic to compare against the frozen prior render. Distinguish a factual pass from an aesthetic preference in the record. Its demand for a substantive weakness applies to full design iteration, not every tiny patch: on a full iteration, name the failures the evidence actually shows and make one substantive correction when one is warranted. An evidence-backed stop at the revision cap is a valid close, and a genuinely clean iteration is recorded as clean; never invent a flaw to fill the record or silently rework past the cap. The adversary never compels a harmful change: its veto must name the specific harm with evidence - the state and the pixels where it occurs. REX capture acceptance, clearer first-view comprehension and a higher taste score are separate outcomes; report each from its own evidence.
## Visual mode: an art-directed experience

Begin with a one-sentence visual thesis tied to the subject: what the viewer sees immediately, what changes if anything, and why that form belongs to the story. When a full concept comparison is warranted, sketch two structural compositions with different narrative rhythms; pick one for its message rather than fashion. Plan a visual system across the *whole* page: type scale and contrast, authored imagery or source-licensed assets where available, crop at desktop and mobile, color and texture, section transitions, and motion only when it has a purpose. Visual mode aims for an authored experience; it need not animate when stillness serves the subject better. Choose the motion mechanism from the page's story: entrance, state change, cursor or gesture, timeline, or scroll. A continuous visual control should map its reported value to a visible progress state, work in reverse and from the keyboard, and update immediately rather than becoming inert when motion is reduced. For a multi-parameter Visual scene, make each control change a distinct visible property and keep the combined state readable in text. Exercise each axis separately, their joint extremes and reversal; make the current values accessible without depending only on color or motion. A decorative multi-slider that leaves the art essentially unchanged is not a meaningful interaction. A two-state physical metaphor can use a reversible local control rather than scroll pinning: verify opening, midpoint, final resting state, reverse path and keyboard activation, and keep any toggle label and pressed state aligned with the rendered art. CSS motion is acceptable when it genuinely expresses the concept; a library or a canvas is not a quality credential. When scroll-driven choreography actually explains the narrative, use GSAP with ScrollTrigger and design the pinning, scrub, and scene transitions around the content. Do not add a stock GSAP scroll sequence to every Visual page; repeated reveal recipes feel like a template. Record why GSAP scroll is used or why another motion mechanism fits better. If the idea needs 3D, use geometry, lighting, occlusion and camera movement that make depth legible; a flat disc with 3D-sounding copy is not a substitute. Inspect changed pixels from at least two camera positions and an actual motion interval, not just the presence of Three.js or a WebGL canvas. Keep a readable static fallback and test a rendered reduced-motion state. Exercise both initial asset/renderer failure and a later graphics-context loss or equivalent runtime failure; do not leave active controls over an inert canvas or call an unloaded scene complete. For ambient motion that runs longer than a brief transition, give the viewer a visible pause/resume control without hiding meaning. The paused image should remain a valid composition, and the control label and pressed state must agree with actual computed animation state. Respect reduced motion at initialization and after a preference change; do not restart against the viewer’s choice when a tab regains focus. Hide a script-dependent pause control until initialization succeeds, leaving a readable static scene without JS. Test moving frames, paused frames separated by time, resume, keyboard activation, narrow layout and reduced-motion pixels. Avoid motion that hides information or blocks controls; keep the final scene coherent at any scroll position. Evaluate the first viewport in the actual delivery frame, not only the page iframe or isolated local tab. A host header, safe area or embedded card can consume much of a phone screen; inspect how much of the central visual behavior and primary route remain visible at 390px and the intended device height. If the artwork appears only after scrolling, rebalance vertical spacing, copy and artwork placement rather than calling a cropped heading a complete first impression. Keep the page readable when the host shell changes size; do not solve the crop by shrinking text below a usable size. The first viewport should communicate the idea without an explanation paragraph, and later sections should sustain it rather than reverting to generic cards. Use an original asset when imagery is central and a suitable tool is available; record origin, license/ownership, size, performance cost, and graceful fallback. Do not fake brands, reviews, sales numbers or product screenshots. No random decoration or borrowed layout in place of a concept.

## Targeted visual failure cases

Load [Visual review cases](references/visual-review-cases.md) only when its trigger fires: the brief or implementation makes a visual claim involving data relationships, physical or causal geometry, transformations, continuous controls, animation, or multi-state rendered evidence, or the work touches one of its specialized interaction workflows (tables and paged results, sequence editing, bulk actions, source reconciliation, destructive or approval flows, offline queues, sensitive records, multi-account actions, imports and exports, collaborative or optimistic writes, settings and permissions, dependent controls and branching, time-zone instants, session expiry). Apply only the matching cases. Routine, static, and ordinary Production UI work should not load this specialized reference; use the applicable mode, accessibility, state-coverage, and rendered-result guidance instead.

## Production mode: dependable pages

For Production briefs centered on a running task or agent, present the history of **one actual run** as a timeline: started, running, each observed event, result or failure, and any unknown outcome. Keep confirmed receipts inspectable and uncertainty visible in place. A set of selectable demo states is not a run and cannot prove continuity, recovery or outcome. Synthetic fixtures may test the UI, but label them and do not present them as real service evidence.

Identify who acts, the exact decision or task, data provenance, constraints and safe completion condition. Map entry, action, feedback and recovery before styling. Build a state coverage ledger; implement relevant loading, empty, error, invalid, success, permission and long/dense cases with truthful messages and preserved input. Avoid status/color contradictions. Keep the next safe action visible or reachable at narrow widths and 200% zoom. Use semantic controls, focus, keyboard, labels, contrast and touch targets, and test both pointer and keyboard paths. Visual decisions should reduce scanning and reveal the task's own shape, not add chrome for its own sake. Render real data-shaped cases at narrow and wide sizes and inspect the pixels and behavior. Never claim live data, verified permissions or production readiness from a local static demo.

## Brief and audit

Identify the audience, primary task, constraints, device sizes, and success measure. Mark assumptions when the brief is thin; ask if an assumption changes the product's purpose or audience. Inspect existing routes, components, tokens, assets, and conventions. For redesigns, capture the current UI and name concrete failures in hierarchy, navigation, readability, responsiveness, accessibility, or task completion. Preserve working content and flows. Never invent testimonials, metrics, logos, prices, or product claims.

## Interaction before styling

Map entry, decisions, primary action, outcomes, and recovery. Cover loading, empty, error, success, disabled, and long-content states where relevant. Dashboards need legible status, freshness, filters, and next actions. For async filters or refreshes, distinguish the requested view from the displayed snapshot while loading or after failure; label retained data as a previous snapshot and keep its counts paired with its rows. Ignore stale responses when a newer request has superseded them, then test a rapid filter change, failure, and actual retry. A mock timer is not proof of live freshness or service recovery. For a chart or metric, mark data provenance and denominator, distinguish missing from a recorded zero, and do not compute a continuous trend or adjacent-period change across an unrecorded gap. Keep exact values accessible in text or a table. Forms need clear requirements, errors, and input preservation. Bind every local review to the exact record, values, account and revision it checked, and invalidate that review when any of them change; a passing local check is not the person's approval, a service acceptance, or permission to commit money. If there is no save service, omit write actions rather than displaying a plausible but inert control. For the specialized workflows - tables and paged results, sequence editing, bulk actions, source reconciliation, destructive and approval flows, offline queues, sensitive records, multi-account actions, imports and exports, collaborative and optimistic writes, settings and permissions, dependent controls and branching, time-zone instants, and session expiry - apply the matching cases in [Visual review cases](references/visual-review-cases.md).


### Choose a craft system

Before styling, state the craft system the brief earns and record the values with their rationale in the review record, not in a separate spreadsheet. Ground the choice in the existing product: reuse its tokens, type and spacing where they exist, and inspect the content's density, the longest real labels and code, the audience, the evidence form, and the crop. When no system exists, choose one for this brief: a small spacing scale with a base step and an optional half step; a coherent typographic range from the smallest essential text to the largest heading; line-height, paragraph and section rhythm; and a grid and gutter scheme appropriate to the content. 8px scales, 12 columns, modular ratios and 45-75ch measures are examples, not mandatory values or hidden house defaults.

Verify the system in actual rendering, not by number alone. Inspect optical spacing, the real font fallback and supported scripts, image crop, and readability and reflow at phone width and zoom; do not declare 11-12px code or 15-16px body text safe by size alone. A section seam should signal the next content job rather than leave an unexplained blank band. Reject and revise the chosen system if it makes unrelated pages look alike, clips long data, erases product specificity, or harms usable density.

Choose a visual direction tied to audience and product. Define a compact system for type, spacing, colors, surfaces, borders, and interaction states. Rank the primary action clearly. Use contrast, alignment, content order, and whitespace before decoration. Do not default to gradients, glass, oversized hero copy, generic AI imagery, or animation instead of hierarchy. Motion should explain state or direction and respect reduced-motion preferences. A reference library is evidence to compare, not a palette of required effects. Choose patterns for the brief and explain what you rejected; do not assume dark glass, bento grids, asymmetry, or hand-drawn textures are inherently better. Keep asset origin, license, responsive behavior, fallback, and performance cost with any adopted reference.

## Learn from examples without becoming one

Collect examples for the actual task, including relevant posts on X when a stable original and rendered result can be inspected, plus studio case studies, live sites, design systems, accessibility standards, and UX research. Record the URL and what was actually observed. A screenshot or promotional case study can show composition and intent; it does not prove conversion, accessibility, motion quality, or production behavior. If X posts cannot be verified, say so and use grounded alternatives instead of attributing an idea to X. Do not copy another skill's language, a site's distinctive graphics, layout, animation sequence, or brand tokens. Extract a mechanism and test it against our own content and user task.

For scroll-led Visual scenes, tie each scroll interval to a distinct content change, inspect actual trigger progress and rendered frames at start, midpoint, end and reverse, and check that pinning exits into the next content without overlap. Recalculate or recheck after responsive breakpoint changes; a desktop scroll proof is not mobile proof. Provide a static script-off and reduced-motion path. For Visual, make a short scene map before coding: each section's message, the object that changes, the reason it moves, the user's control, its final resting state, mobile pacing, and reduced-motion equivalent. Choose among scroll, page transitions, hover/focus, gesture, and state change. GSAP ScrollTrigger is fitting when scroll progress *is* the story; its pin/scrub/snap features are options, not a checklist. If the same reveal or pin could be swapped into any brand unchanged, revise the concept. Measure asset weight and check slow-load/failure fallback along with start, middle, end, and reduced-motion pixels. Non-essential scroll/parallax motion must be suppressible, not merely slowed down.

For Production, study examples for error prevention and recovery, not visual polish alone. Separate user input errors from app/service failures and incompatible or permission states. State requirements before entry; validate after enough input or on blur rather than marking unfinished typing wrong. Clear an error as soon as the corrected value is valid, preserve the rest of the form on failure, and provide a concrete recovery step. For a write that times out after dispatch, distinguish unknown outcome from confirmed failure: retain the draft and request identity, check the same operation before offering a retry, and do not issue a second write with a new identity merely because the response was lost. A weak eventually consistent "not found" is still unknown; retry needs a conclusive service status or a service-enforced idempotency contract with the same key. Local UI state alone proves neither. A retry label must correspond to a real retry path; if a mock always fails, say so and do not promise that retry will help. In a simulation, distinguish a local check from a saved or submitted record in both the action label and success copy. Exercise failure, retry, and the resulting state rather than inferring recovery from a visible button. After filtering to zero results, clear filters and confirm both the input and the rows reset; move focus to an actual recovery control when results disappear, and confirm keyboard activation restores the view. Test failure and retry with the existing filter state intact. If a form field name or ID overlaps a native method such as reset, check that the clear action still works. Keep visible totals distinct from filtered totals so the summary cannot mislead. Client-side validation aids usability but never replaces server validation; visual status changes alone do not prove that assistive technology announces them. Exercise the actual correction, failed submission, retained input, focus/announcement and return path before marking a flow done. Adapt any checkout research only to similar inputs and risks.

## Reference transfer test

For every outside reference, write down the user problem it solves, the mechanism worth borrowing, and the part that does not fit this product. Translate the mechanism into the product's own content, controls, and design tokens rather than copying its layout. Test the translated idea against the same task and edge state in the current UI. If it hides an action, needs invented content, weakens keyboard use, or breaks narrow screens, reject it even if the reference looks impressive. An adopted pattern needs a reason grounded in the task, not a similarity score.

## One product-specific interaction

Before choosing type or colors, consider whether a central behavior lets the person understand or change their task better than a clear static composition. If not, keep it static. For an interactive direction, name its visible object, governing rule, meaningful action and what happens when data is sparse, wrong or delayed. For a static direction, name the evidence and route. Make the chosen evidence or behavior clear from the first viewport without an explanation paragraph. A distinctive behavior earns its place only when it makes the task faster or safer; an unusual layout that hides a control is not an improvement.

Use external examples to challenge the bar, not to copy art direction. Compare only like-for-like evidence: same task and rendered states for a skill benchmark. If the reference has only a polished desktop image, judge visual presentation against that image, but do not infer its mobile, keyboard, error, or live-product behavior. Record where our build is weaker, where it is stronger, and which dimensions remain unknown. Fix the weakest actionable gap in the next build rather than adding decorative effects.

## Button design

Inspect the product's design system, existing buttons, tokens, and usage first. Preserve its button family and improve role and hierarchy within it; do not add novelty for its own sake. When no system exists, choose form, weight, scale, spacing, typography, and states from the action's consequence, hierarchy, product's visual thesis, and interaction context—not a reusable default or a color/radius swap. Keep primary, secondary, quiet, and destructive roles coherent within the product; pills are valid when they fit, not a requirement.

Compare two treatments only for a greenfield or major redesign, or a focal CTA. Hold the action, label, role, and context constant; vary only one or two design variables. Choose the treatment that best fits hierarchy, product identity, and recognizable affordance—not the one that is merely more unique. When prior rendered examples from unrelated projects are available to inspect, compare their primary buttons side by side: if form, weight, scale, spacing, and type repeat without a task- or brand-based reason, challenge the default; then check that each product's button roles still read as one family. If none are available, do not claim cross-project variation or infer unseen history; state the current brief's action/context rationale instead.

Give icon-only buttons accessible names. Make disabled and loading states reflect real behavior and semantics, not decoration. Verify keyboard focus-visible, hover, pressed, and relevant disabled/loading states, plus adequate target size and spacing at narrow touch widths.

Use buttons for actions and links for navigation. Label each button with its action and outcome; for destructive actions, name the affected item and consequence in text—never rely on color alone.

## State coverage ledger

Before coding, make a short ledger with one row per consequential state. Use these columns: user intent, entry point, data condition, visible feedback, next action, narrow-screen behavior, and proof. At minimum cover first use, normal use, no results, invalid input, failure, and a long or crowded case where they apply. Mark a state not applicable only with a reason. This is a planning aid, not a checklist that substitutes for examining the product.

For each row, check the words, data, and visual signal together. A passing fact cannot be styled as failed; a blocked completion cannot be labeled open or complete. If the primary control falls below the first viewport on a narrow screen, offer an honest visible route to it instead of hiding the recovery. At 200% browser zoom, check reflow, horizontal clipping, and reachable controls; a narrow screenshot or compositor page scale alone is not that test. If actual zoom cannot be exercised, use a half-width CSS-viewport proxy to find likely reflow defects, but label the true zoom result unverified.

For each row, ask whether the user can tell what happened and recover without losing their work. Prioritize a broken task or inaccessible control over decoration. If the task is only a visual critique, use the ledger to name missing states instead of pretending they were implemented. When handing off code, distinguish states actually exercised in the rendered UI from those inferred from source or left untested.

## Design decisions under pressure

Use the [pre-build concept gate](#pre-build-concept-gate) to decide whether a full concept comparison is warranted and how to record its trade-offs; the gate defines narrow (one component or state, with the existing experience as the baseline) and the changes that force the full gate (first view, information hierarchy, promised outcome). If the brief does not support a confident choice, show the decision to the product owner rather than inventing a user preference.

## Implement and verify

Reuse components and tokens where possible. Use semantic elements, real labels, keyboard access, visible focus, sufficient contrast, sensible tab order, and usable touch targets. Check narrow, medium, and wide layouts instead of shrinking desktop. Handle long labels, zero results, and realistic data density; preserve routing and state behavior.

**Freeze the supported width range before review.** Declare the intended supported widths in the review record before the first visual check; the range cannot be narrowed after seeing a failure. Render the host-framed first view and the settled full page at 1440px, the default wider stress width 1920px, 390×650, and the default smaller phone 320px, plus the medium widths between breakpoints. The 1920px and 320px stress widths are defaults, waivable only with a recorded reason tied to the brief's audience and devices; a waived default is declared in the record, not silently dropped.

### Image semantics and delivery

Set alternative text by role and context: informative images get concise alt text conveying essential information; decorative or redundant images use `alt=""` and do not repeat adjacent text. For an image-only control, provide an accessible name that conveys its action (button) or destination/purpose (link). Charts and diagrams that carry substantial information need an equivalent text/data explanation, such as an adjacent long description or structured table ([W3C Images Tutorial](https://www.w3.org/WAI/tutorials/images/), [WHATWG alt guidance](https://html.spec.whatwg.org/multipage/images.html#alt)). Use responsive sources only when viewport-specific resolution or art direction warrants them ([MDN responsive images](https://developer.mozilla.org/en-US/docs/Web/HTML/Guides/Responsive_images)). Reserve the image's aspect-ratio space before load with intrinsic dimensions or an equivalent layout constraint; lazy-load noncritical offscreen images, not critical first-view imagery ([MDN `<img>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/img), [MDN lazy loading](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/Lazy_loading)). Inspect loaded and broken-image presentation in rendered output.

Run relevant checks, then render the actual UI. Inspect the host-framed first view and the settled full page at the frozen range's declared sample widths, with probes at each breakpoint edge and in the intervals between breakpoints, not merely hero screenshots. Exercise the primary path with keyboard and pointer, plus an error or empty state and long content; inspect between-breakpoint overflow, the right edge, any code panel, section seams, image crop, labels and all consequential states. Fix issues and inspect the changed result. Real browser 200% zoom is a separate test from a half-width proxy (see [State coverage ledger](#state-coverage-ledger)); retain the text-only resize and text-spacing override checks in [Typography and text adaptation](#typography-and-text-adaptation). For embedded or hosted pages, compare the actual host-shell rendering before and after, including shell background/text, link and control colors (visited and unvisited), and keyboard `:focus`/`:focus-visible` indicators. Host CSS can override local declarations; treat unintended shell changes as a blocker and keep shell styling outside the app scope. Source code, DOM, or a successful build alone cannot prove visual quality. Source-pattern and symmetry scores can catch known mistakes but do not measure task fit, accessibility, or visual quality; never use them as a pass certificate or optimize a page merely to raise a score. If rendering is unavailable, explicitly mark the visual work unverified.

### Typography and text adaptation

For text-heavy views, tune line measure, leading, and paragraph spacing together against realistic copy in the chosen typeface and viewport; use a different rhythm for extended reading than for labels, captions, or display text. Treat character-count targets (for example, [USWDS’s 45–90-character guide](https://designsystem.digital.gov/components/typography/)) as starting heuristics, not fixed tokens. Separately from browser zoom, test text-only resizing to 200% without loss of content or functionality ([WCAG 2.2 SC 1.4.4](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)). For the text-spacing check, apply these together as user overrides, not author defaults: line height of at least 1.5× font size, paragraph spacing of at least 2× font size, letter spacing of at least 0.12em, and word spacing of at least 0.16em, where applicable to the writing system. Report clipping, overlap, reduced readability, or hierarchy loss, and ensure truncated content remains available ([WCAG 2.2 SC 1.4.12](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html)).

### Localization and language resilience

When the interface is localized or accepts locale-specific content, stress-test text expansion with realistic longer strings in each supported writing direction and the actual font fallback. Let labels, validation, errors, and buttons reflow; do not hide meaning through truncation, clipped glyphs, or illegible shrinking. Use locale-aware dates, numbers, currency, units, and plural forms rather than concatenating translated fragments. In right-to-left layouts, verify reading order, input direction, mixed-direction identifiers, and directional icons or controls; mirror only what should change direction—do not reverse semantic sequences, values, keyboard/focus order, or brand marks by default. If a locale or script cannot be tested, mark it unverified; do not imply localization support. When localization is out of scope, this is not a gate.

## Evidence and review

Keep a small, reproducible review record for changed flows: viewport width and zoom; the starting route and data state; the action attempted; what the rendered UI showed; and whether the user could finish or recover. Capture the before and after for the same task, not only the best-looking final frame. If a visual choice trades away task speed, density, or clarity, name that cost and who bears it.

Before critique, record the success criterion, the scope and stage under review, and the feedback requested. The reviewer zooms out first - task, hierarchy, identity and cross-width unity - then in: text, geometry, semantics and recovery. For a marketing first scan, hide the branding in a timed host-framed crop and test whether the task, the proof and the next action read; do not infer conversion from 50ms appeal studies. A blinded non-builder reviewer answers the same fixed questions on both arms of a comparison; preserve their verbatim answers, not the maker's confidence. Arms are the compared variants of a comparative validation; a narrow patch has none, and a compact route and status note is enough for it. The builder must not simulate the blinded reviewer: when no non-builder is available, record the blinded review as not performed and the verdict as provisional. Walk the actual pixels and actions as a first-time visitor on desktop and phone, with source and receipt readbacks and the applicable error recovery.

Critique with KEEP / CHANGE / CUT. KEEP names the actual pixels or behavior worth preserving and why; keep the KEEP set unchanged through revision unless evidence names why altering one item helps. CHANGE identifies the state or crop, the observed flaw, the minimal fix, before/after pixels and a task regression check. CUT names a distracting or redundant element. **No CUT and no CHANGE are valid outcomes** when nothing useful needs changing or cutting: stop rather than perform ritual revisions. A targeted fix gets a new capture and action readback at the affected states. Ask a reviewer to challenge the weakest state or assumption instead of voting on polish alone. No automated checker, screenshot, or single happy-path demo proves a design works for its audience. When using REX custody, compare the final page and review with the task and acceptance frozen at execute. If the central behavior changed, do not treat a file receipt or accepted submission as proof that the original design obligation was met; report the mismatch and seek an explicit revised task or narrower claim.
